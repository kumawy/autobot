# Freedom Pay: контракт v1.1

Проверка публичной документации: **2026-10-01**. Сценарий — Merchant API Казахстана, hosted checkout через `init_payment.php`, окончательное списание в один этап (`pg_auto_clearing=1`). Реквизиты карты приложение не принимает. Совместимость конкретного merchant account и его тестовые операции ещё нужно проверить в sandbox провайдера; локальные fixtures не заменяют эту проверку.

## Источники и выбранный протокол

- [Merchant API overview](https://docs.freedompay.kz/overview-741636m0): подпись и транспорт.
- [Создание платежа](https://freedompay.kz/docs/merchant-api/pay): параметры hosted checkout, идентификаторы и idempotency key.
- [Result notify](https://docs.freedompay.kz/result-notify-12007677e0): входящий form-data, XML-ответ, повторные уведомления.
- [Status](https://docs.freedompay.kz/status-11620963e0): `get_status3.php`, финансовый статус, capture и отдельные операции возврата.

`pg_status=ok` подтверждает выполнение API-запроса. Финансовый результат читается из `pg_result` в callback или `pg_payment_status` в status response. Авторизация карты без окончательного списания не оплачивает заказ. Уведомление без признака capture проходит дополнительную серверную проверку. Ответ по bankcard без достаточного подтверждения capture требует проверки; неизвестное значение не угадывается.

Исходящие create/status отправляются как multipart/form-data. Callback принимает ограниченный multipart с текстовыми полями, без файлов, а также urlencoded/XML варианты старого Merchant API. JSON не является основным контрактом Freedom Pay. Парсер не удаляет дополнительные поля перед проверкой подписи. Повтор одного поля, чрезмерная глубина, XML entities/DOCTYPE и слишком большой документ отклоняются.

## Поля и принадлежность платежа

| Поле провайдера                             | Назначение в приложении                                                                                                                                                              |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pg_merchant_id`                            | Настроенный merchant; если поле возвращено, его значение проверяется. Когда метод его не возвращает, используются проверенная подпись и контекст запроса с настроенными credentials. |
| `pg_order_id`                               | Уникальный неизменяемый `PaymentAttempt.merchantReference`, максимум 50 символов. Не номер заказа для клиента.                                                                       |
| `pg_idempotency_key`                        | `init:<attemptId>`; сохраняется при повторах одной попытки.                                                                                                                          |
| `pg_payment_id`                             | Внешний ID платежа, закрепляемый за конкретной попыткой.                                                                                                                             |
| `pg_amount`, `pg_currency`                  | Фактические сведения. Десятичная сумма остаётся строкой; сравнение без `parseFloat`, округления и преобразования в binary float.                                                     |
| `pg_result`                                 | Результат уведомления; `1` допускает оплату только после остальных проверок, `0` означает неуспех.                                                                                   |
| `pg_payment_status`                         | Финансовый статус при сверке; отдельно от `pg_status`.                                                                                                                               |
| `pg_captured`                               | `0` — авторизация/ожидание; `1` — подтверждение списания в поддерживаемом карточном сценарии.                                                                                        |
| `pg_refund_payments`, `pg_revoked_payments` | Отдельные refund/reversal операции; собственный ID, статус и точная фактическая сумма каждой сохраняются отдельно.                                                                   |
| `pg_salt`, `pg_sig`                         | Salt и подпись, обязательные для проверки.                                                                                                                                           |

До первого HTTP create БД содержит snapshot заказа, `orderVersion`, сумму, валюту и merchantReference. Эти данные неизменяемы. Для применения оплаты сервис сравнивает данные с попыткой и текущей `contentVersion` заказа. Сумма `20000.01` не равна `20000`; научная запись, запятая и числовое дробное значение JavaScript не принимаются как точная денежная сумма.

Status response может не содержать `pg_order_id`. Для сверки по известному внешнему ID достаточны подписанный ответ на запрос этого ID, совпадение ID, merchant-контекст и проверка суммы/валюты. Выдуманное обязательное поле не добавляется. При сверке неизвестного результата создания используется уникальный merchantReference; отсутствие или ошибка ответа не доказывает, что create не выполнялся.

Для мигрированных v1.0 попыток допускается прежний `pg_order_id=orderId` **только** при сохранённых `snapshot.legacyMigration=true`, `snapshot.legacyMerchantReference`, совпадающем известном внешнем payment ID. Этот механизм не связывает неизвестные платежи с заказом по сумме или телефону. Исторические Freedom Pay attempts с `merchantId=demo` требуют явной миграции merchant account оператором.

## Подпись

Вход: basename вызываемого script, значения всех параметров в алфавитном порядке имён, затем secret; разделитель `;`, результат MD5 в lower case. Вложенные поля сортируются рекурсивно, одинаковые XML-теги сохраняют порядок. Только `pg_sig` исключается. Проверка сравнивает подписи через timing-safe comparison.

Callback basename берётся из настроенного публичного URL `/webhooks/payment/freedompay`: в этой конфигурации это `freedompay`. Произвольные `Host`, `Forwarded` и другие заголовки не меняют подписываемое имя. Прокси должен сохранять согласованный callback URL. Подписанные XML-ответы create/status также проверяются.

## Приём события, ответ и восстановление

1. Проверить подпись, получить нормализованное событие, сохранить `WebhookEvent` с `authenticatedAt`, hash и статусом `RECEIVED`.
2. Если не хватает суммы, валюты или подтверждения capture — выполнить status HTTP **после завершения транзакции**. Платёж до проверки не применяется.
3. В короткой транзакции заблокировать заказ и применить общий финансовый переход. Зафиксировать incident/outbox и первый успешный XML acknowledgement вместе с `PROCESSED`.
4. Повтор возвращает сохранённые байты XML. Новый salt запроса не создаёт повторное логическое подтверждение.
5. Сбой после сохранения inbox восстанавливает `PAYMENT_EVENT`; незавершённые платежи сверяет `PAYMENT_RECONCILE`. Для задания проверяются token, lease и его текущий владелец в транзакции применения. Старый worker не может применить поздний HTTP-ответ после перехвата lease.

| Ситуация                                          | Ответ callback / состояние                                                                                                                                      |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Невалидная подпись / недопустимый транспорт       | Технический отказ; финансовых изменений нет.                                                                                                                    |
| Валидный результат, завершённая запись БД         | HTTP 200, подписанный XML `pg_status=ok`; ответ сохранён.                                                                                                       |
| Подлинный mismatch/unknown/duplicate/late payment | HTTP 200 после сохранения фактов и инцидента; заказ удерживается для проверки. Это не команда вернуть деньги.                                                   |
| БД недоступна / сверка временно недоступна        | HTTP 503 и подписанный XML `pg_status=error`; нет успешного подтверждения приёма. Сохраняемый технический RETRY не считается окончательным финансовым решением. |
| Повтор завершённого результата                    | Первоначальный сохранённый acknowledgement, без нового подтверждения клиенту.                                                                                   |
| Другая фактическая сумма под тем же ID результата | Сохранённое подтверждение и отдельный инцидент с конфликтующими фактическими данными.                                                                           |

Приложение не отправляет `rejected` и не вызывает автоматический refund/cancel API. Локальная отмена заказа не отменяет внешнюю платёжную ссылку. Отказ до успешного приёма уведомления не является утверждением, что платёж отменён.

Timeout, разрыв соединения, HTTP 5xx, непроверяемый ответ или небезопасный redirect после create означают `CREATION_UNKNOWN`. Только проверенный подписанный отказ create классифицируется как `CREATION_REJECTED`. Система не создаёт новую попытку вслепую. Если найден ожидающий платёж, но status API не вернул исходную hosted URL, создаётся `CREATION_RECOVERED_NO_URL` для менеджера.

## Финансовые решения

Первое подтверждённое поступление оплачивает неизменённый заказ и закрепляет `appliedPaymentAttemptId`. Поздний `FAILED/PENDING` не отменяет `PAID`. Этапы `PROCESSING/SHIPPED/COMPLETED` не переводятся назад.

Другая оплаченная попытка сохраняется как отдельное поступление с `DUPLICATE_PAYMENT`, без второй продажи. Оплата отменённого заказа сохраняет `orderStatus=CANCELLED` и `paymentStatus=PAID`, создаёт `LATE_PAYMENT`, hold и обновление той же строки Sheets. При неверных сумме/валюте/merchant/version попытка получает `REVIEW_REQUIRED`; фактические значения остаются в инциденте.

Подтверждённые refund/reversal операции не превращаются в обычный failed callback. Они сохраняются отдельно и ставят hold для ручного разбора; адаптер не вычисляет окончательное нетто-состояние заказа и не обещает клиенту возврат. Исторический подтверждённый capture остаётся в финансовой истории. Решение инцидента требует автора и комментария и не подделывает оплату/возврат. Hold нельзя снять при другом открытом финансовом инциденте. `REVIEW_REQUIRED` не разрешает новую автоматическую попытку; требуется сверка и ручное решение.

Сверка учитывает `PAYMENT_RECONCILE_INTERVAL_MS`, `PAYMENT_RECONCILE_BATCH_SIZE`, `PAYMENT_PROVIDER_MIN_INTERVAL_MS`. Общий `beforeStatusRequest` ограничивает частоту status запросов из worker и callback. `Retry-After` передаётся планировщику. Реальный допустимый интервал и лимиты согласуются с merchant account; один процесс не обходит общую координацию нескольких worker.

## Fixtures и приёмка

Обезличенные локальные fixtures: [unit providers](../../tests/unit/payments.test.ts), [PostgreSQL financial integration](../../tests/integration/payments-v11.test.ts). Значения `merchantId=999`, `shop.example`, secret с пометкой fixtures — синтетические. Тесты проверяют независимый известный вектор MD5, изменение/добавление поля, callback basename, подписанный XML, exact decimals, создание с неопределённым исходом, повтор acknowledgement, durable retry/replay, владение lease и финансовые инциденты. В них нет настоящего HTTP-запроса в Freedom Pay.

Перед live merchant должен подтвердить одностадийный capture, валюту, callback path, test/live ключи, методы оплаты, поведение status lookup по reference, частоту запросов, состав полей и реальные повторные callbacks. Sandbox-протокол с обезличенными исходными ответами добавляется после проверки реального аккаунта; текущая реализация не объявляется сертифицированной провайдером.
