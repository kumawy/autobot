# Проверка готовности v1.1

Текущая поставка рассчитана на локальный запуск с демонстрационными данными. Наличие кода адаптера и успешные тесты с подменой HTTP не подтверждают доступ к merchant-аккаунту, одобрение шаблона или доставку реального сообщения.

| Статус | Необходимые основания |
|---|---|
| `LOCAL_READY` | Локальный симулятор, миграции PostgreSQL, typecheck, lint и тесты проходят; реальные деньги не принимаются. |
| `INTEGRATION_READY` | Настроены и проверены реальные аккаунты, callback-контракт Freedom Pay, доступные шаблоны RU/KK, двусторонний Telegram bridge и разрешённые тестовые операции. |
| `PRODUCTION_READY` | Дополнительно утверждены каталог, состав комплекта, доставка и обработка данных; проверены резервное копирование и восстановление, HTTPS и доступ сотрудников; владелец провёл допустимые провайдером контрольные операции и зафиксировал результаты. |

## Автоматическая диагностика

Используйте закреплённый **Node.js 24.21.0**, указанный в `.nvmrc`. Команда выполняет чтение настроек и проверочные запросы; платежи и сообщения не создаёт:

```sh
npm run check:production
```

Для сохранения чистого JSON без служебной строки npm:

```sh
mkdir -p .local/readiness
npm run --silent check:production > .local/readiness/check-production.json
```

Код завершения `1` и `ready:false` в demo ожидаемы: нет внешних ключей, runtime использует mock, каталог и бизнес-данные демонстрационные. Это не означает сбой локального проекта. Исправляйте причины в отчёте, а не заменяйте недостающие ключи фиктивными значениями.

| Результат проверки | Значение |
|---|---|
| `OK` | Указанная узкая автоматическая проверка выполнена. |
| `MISSING_CONFIGURATION` | Нет обязательного значения или доступного варианта шаблона. |
| `INVALID_CONFIGURATION` | Значение, runtime, бизнес-данные или структура Sheets не соответствуют требованиям. |
| `ACCESS_FAILED` | Проверочный запрос или доступ к БД не завершился успешно. |
| `MANUAL_TEST_REQUIRED` | Требуется проверка владельцем с реальным аккаунтом и сохранённым результатом. |

**Текущая команда всегда оставляет обязательные ручные проверки `MANUAL_TEST_REQUIRED` и потому сама не выдаёт `ready:true`.** Она не читает файл «подтверждения» и не превращает выставленный вручную флаг в доказательство. Итоговую готовность определяют по отчёту вместе с протоколом проверок владельца. Вывод `OK` для БД или модели не является разрешением принимать оплату.

Автоматически проверяется:

- Наличие обязательных настроек; `NODE_ENV=production`, `INTEGRATION_MODE=live`, `PAYMENT_PROVIDER=freedompay`, `FREEDOMPAY_TEST_MODE=false`; HTTPS для приложения и платёжного API; точное совпадение Node с `v24.21.0`.
- Доступ PostgreSQL и наличие заказов, ожидающих переноса старых строк Sheets. Неуспешный запрос также может означать, что миграции не применены.
- Утверждённые бизнес-данные и готовность каталога: реальные условия вместо demo/TODO. `RETENTION_APPROVED` отражает решение владельца об обработке данных, а не проверку законодательства программой.
- Доступ service account к Google Sheets, sheet ID, название технического листа, защита и заголовки A:Y. Скрипт не выполняет тестовую запись.
- Реестр трёх назначений шаблонов для RU/KK и статус `APPROVED` пары «имя + locale» в Meta. Проверяется первая страница, до 100 шаблонов; если нужный шаблон находится дальше, требуется ручная проверка аккаунта. Текст и параметры утверждённого шаблона дополнительно сверяются человеком.
- Доступность настроенной OpenAI-модели через запрос сведений о модели. Это не проверяет фактический вызов Responses API, квоты или качество RU/KK-ответов.
- Telegram: `getMe`, наличие разрешённых менеджеров в выбранном чате и URL из `getWebhookInfo`. У бота должны быть права для проверки участников. Сам секрет webhook через этот метод прочитать и подтвердить нельзя.

Инструкции настройки: [WhatsApp, Telegram и Sheets](integrations/whatsapp-telegram-sheets.md), [Freedom Pay](integrations/freedompay.md), [OpenAI](openai.md), [развёртывание](deployment.md).

## Обязательный протокол владельца

Сохраните дату, исполнителя, окружение, версии приложения и конфигурации, обезличенные идентификаторы событий и ожидаемый/фактический результат. Закройте доступ к доказательствам посторонним. Не включайте API-ключи, PAN/CVV, коды подтверждения или полный клиентский адрес. Можно хранить протокол в `.local/readiness/`; эта папка не предназначена для публикации.

1. **Freedom Pay:** подтвердить используемый merchant-контракт и окончательное списание; проверить подпись callback/status, подписанный XML-ack, повтор callback, задержанный результат и сверку после потерянного ответа. Авторизация/hold не считается оплатой. Контрольная оплата и события возврата проверяются разрешённым провайдером способом; приложение не выполняет автоматический refund. Самостоятельно подписанный mock не доказывает совместимость реального merchant API.
2. **WhatsApp:** для RU и KK проверить реальный locale, имя и параметры каждого шаблона; получить обычный ответ внутри окна, допустимый шаблон вне окна, блокировку при отсутствии шаблона/согласия, отказ от уведомлений и фактические delivery receipts. Убедиться, что «принято API» и «доставлено» различаются.
3. **Telegram:** два клиента и два менеджера; принятие обращения, Reply правильному клиенту, отклонение чужого/неназначенного отправителя, неверного secret и повторного update, закрытие ticket и отмена отложенного ответа, неподдерживаемое медиа. Проверить поведение вне окна WhatsApp.
4. **Sheets:** правильная строка после оплаты, повторная запись в тот же binding, обновление версии и инцидента, защита от физической сортировки/удаления/вставки менеджерами. Для v1.0 сначала выполнить перенос исторических bindings и дождаться актуальной записи A:Y. Не удалять блокировку старого заказа вручную ради обхода сверки.
5. **Эксплуатация:** восстановить PostgreSQL из резервной копии в отдельное окружение; проверить worker heartbeat, восстановление lease, `UNKNOWN`/`DEAD`/`BLOCKED`, ограничения admin API и журнал ручных действий. Утвердить сроки хранения, круг сотрудников, способы исправления/удаления данных и размещение инфраструктуры. Убедиться, что demo endpoints недоступны в production.

Обработка уже существующих платежей и консультации не должны прекращаться из-за незаполненного нового каталога; создание новой реальной оплаты при неутверждённых условиях блокируется. Исправление бизнес-данных не меняет сохранённую сумму и состав уже зафиксированной попытки.

## Переход со старой таблицы

Остановите worker и все записи в технический лист, сделайте резервные копии БД и Sheets. Обновите заголовки до A:Y, затем запустите `npm run sheets:migrate` без `--apply`. Отчёт `.local/sheet-migration-report.json` содержит совпадения, конфликты и безопасный следующий номер строки.

При любом конфликте — дубли, неизвестный/отсутствующий Order ID, неверная сумма/валюта или другое назначение binding — ничего не применяется. После исправления и повторного отчёта без конфликтов выполните `npm run sheets:migrate -- --apply`.

Применение повторяемо: существующие корректные bindings сохраняются, cursor никогда не уменьшается. Исторические заказы переходят в `PENDING` и получают только задание обновления Sheets; подтверждения оплаты повторно не отправляются. После запуска worker они получают полный текущий снимок A:Y. До завершения этой записи миграция не объявляет данные `SYNCED`.

Блокировка cursor защищает распределение строк в БД, но не останавливает внешнего редактора Google Sheets. Поэтому остановка записей на время чтения отчёта и его применения остаётся обязательным условием процедуры.
