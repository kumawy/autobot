# ТЗ: подключение существующего WhatsApp Business к боту на Railway

Дата: 6 октября 2026 года. Версия: 1.0.

## 1. Решение и область работы

По итогам обсуждения выбран Baileys — связывание существующего номера через QR-код как дополнительного устройства WhatsApp Web. Документов бизнеса у владельца нет; платный WhatsApp-провайдер не используется. Пользователь поручил переделать существующий проект после рекомендации этого варианта.

Это неофициальное подключение с возможными отключениями и блокировкой аккаунта. Для первичной проверки использовать тестовый номер. Railway и AI имеют отдельные расходы.

Существующий сценарий музыкальных шкатулок, языки RU/KK, оформление заказа, AI, платежные проверки, Google Sheets и Telegram сохранить. Новый сценарий владелец добавит отдельно. В доработку входят транспорт WhatsApp, управление ручными ответами и конфигурация Railway. Рассылки, новая CRM, несколько номеров и расшифровка голосовых не входят.

## 2. Архитектура

Клиент WhatsApp → Baileys → существующий durable inbox PostgreSQL → обработчик сценария/AI → outbox → Baileys → клиент.

- Использовать существующий интерфейс `WhatsAppTransport`; сохранить транспорт `cloud` для будущего официального API.
- Выбирать транспорт переменной `WHATSAPP_TRANSPORT=cloud|baileys`.
- В Baileys запускать HTTP, worker и socket одним `npm start` в одном Railway-сервисе.
- Использовать PostgreSQL для очередей, состояний, заказов и зашифрованной авторизации.
- Допускать только одного владельца одной сессии, с контролем lease и остановкой связи при утрате владения.

## 3. Подключение и доступ

- Создать страницу `/whatsapp/connect`: вход по ключу администратора, QR, состояние номера, восстановление подключения и список последних диалогов.
- Выдавать QR и данные диалогов только через API с `Authorization: Bearer <ADMIN_TOKEN>`; не включать секреты в URL, журналы или публичный HTML.
- Хранить токен страницы только в памяти текущей вкладки. Ответы административного API не кэшировать.
- Проверять отсканированный номер по `WHATSAPP_EXPECTED_NUMBER`, если параметр задан.
- В Baileys отключить Meta webhook для входящих сообщений, чтобы сценарии не запускались синтетическим Cloud-событием.

## 4. Сессия и устойчивость

- Сохранять Signal-ключи и credentials в PostgreSQL с AES-256-GCM. Ключ — отдельная переменная окружения из 32 случайных байт в hex.
- Восстанавливать авторизацию после перезапуска без нового QR, пока связанное устройство не отключено владельцем/WhatsApp.
- При временном разрыве переподключаться с увеличением паузы до 30 секунд.
- При выходе из аккаунта ожидать явного восстановления и нового QR; не удалять заказы и переписку.
- Пока socket отключён, сохранять задания в очереди без расходования попыток отправки.
- При неоднозначном результате отправки сохранять `UNKNOWN`, не повторять отправку автоматически.
- Сохранять внешнюю идентичность отправки до вызова socket, чтобы ранний echo не считался ответом менеджера.
- При настроенном Telegram уведомлять о выходе из аккаунта, несовпадении номера и сбое хранилища, ограничивая повторы.

## 5. Менеджер

- Ручное исходящее сообщение с телефона переводит только соответствующий диалог в `HUMAN_HANDOFF`.
- Исходящие сообщения самого бота не вызывают handoff.
- Отменять ожидающие консультационные ответы при handoff, проверять режим и актуальную версию диалога перед отправкой.
- Если AI ещё готовит ответ, после ручного перехвата не отправлять этот ответ.
- Для предварительного перехвата предоставить действие «Поставить на паузу».
- Возвращать бота явно: «Вернуть боту» в управлении или существующее закрытие обращения через Telegram.
- Ручной режим не останавливает финансовые callback и разрешённые уведомления по заказу.
- Не обещать отмену сообщения, отправка которого уже началась.

## 6. Меню и сообщения

- Сохранить существующие действия сценария и одноразовые action tokens.
- Преобразовать кнопки/списки в текстовые варианты с нумерацией; клиент отвечает цифрой.
- Привязывать ответ к последнему отправленному меню либо процитированному сообщению данного клиента.
- Сохранить проверки версии, срока, принадлежности и повторного использования действий.
- Не превращать числовые поля заказа в выбор из старого меню.
- Обрабатывать только личные диалоги; игнорировать группы, статусы и служебные события протокола.
- Поддерживать PN/LID-адресацию без подмены opaque LID телефонным номером.
- Не запускать сценарий по сообщениям истории до первого связывания.
- Сохранить поддержку текста, отправки фото и текущую реакцию на неподдерживаемые медиа.
- Не использовать Cloud API-шаблоны через Baileys. Сохранить согласия и запреты устаревших ответов; Cloud-only окно применять только к `cloud`.

## 7. Railway и первый запуск

- Dockerfile, одна реплика, Serverless выключен, перезапуск `Always` на подходящем тарифе.
- Миграции до запуска новой версии; не запускать отдельный worker для Baileys.
- Публичный HTTPS-домен, `HOST=0.0.0.0`, `PORT` от Railway.
- Для первой проверки staging + mock-платежи, без публичных developer routes. Не включать реальные платежи как побочный эффект замены WhatsApp.
- `/ready` проверяет базу; отдельно контролировать socket и heartbeat worker.
- Подготовить резервное копирование базы и хранение ключа шифрования для восстановления.

Настройки и порядок запуска: [BAILEYS_RAILWAY.md](BAILEYS_RAILWAY.md), [baileys.env.example](../baileys.env.example), [railway.json](../railway.json).

## 8. Приёмка

1. Номер связывается через QR; доступ к QR без авторизации запрещён.
2. Клиент получает существующее меню, выбирает язык цифрой и проходит прежний сценарий.
3. Повтор события не создаёт второй заказ/ответ.
4. Ручной ответ ставит нужный диалог на паузу; другие клиенты не затронуты.
5. Ответ AI в процессе подготовки отменяется при перехвате менеджером.
6. Ранний echo отправки бота не вызывает handoff.
7. Явный возврат боту восстанавливает допустимый этап.
8. Перезапуск сохраняет авторизацию, заказы, режимы и очередь.
9. Второй процесс не открывает ту же сессию одновременно.
10. Выход из аккаунта требует нового QR после явного восстановления.
11. Отключённый socket не исчерпывает попытки очереди; неоднозначные отправки не повторяются автоматически.
12. Доставка проверена на реальном тестовом номере, а работа без ноутбука — после развёртывания Railway.

Пункты 1–11 допускают автоматические проверки с PostgreSQL и подменённым socket. Пункт 12 требует реального связывания и развёртывания. Подмена socket не подтверждает доставку в WhatsApp.

## 9. Остающиеся параметры запуска

При реализации приняты: один номер, существующий сценарий, ручные ответы с телефона и управление через защищённую страницу, Telegram опционален. Для подключения владелец указывает сам номер, создаёт/выбирает Railway-проект, задаёт секреты и AI-модель, определяет бюджет и выполняет QR-связывание. Эти данные не должны фиксироваться в репозитории.
