# Эксплуатация v1.1

## Процессы и запуск

Node.js 24.21.0 закреплён в `.nvmrc`, CI, engines/lockfile и образе Docker. PostgreSQL — источник состояния. Приложение принимает webhook и сохраняет события; отдельный worker выполняет inbox, outbox и периодическую сверку. HTTP/AI не держат транзакции БД.

Для локальной демонстрации: `npm ci && npm run demo`, затем http://localhost:3000. Скрипт запускает встроенную PostgreSQL 18.4 на 127.0.0.1:55432, миграции, seed, app и worker. Повторный запуск сохраняет `.local/postgres`. Ctrl+C останавливает процессы. `.env` создаётся с правами0600 и случайными локальными секретами. Демо нельзя запускать с production/live настройками.

Для своей БД: заполнить `.env`, выполнить `npm run db:generate`, `npm run db:migrate`, `npm run seed`, `npm run build`; запускать `npm start` и `npm run worker` под менеджером процессов. При разработке доступны `npm run dev` и `npm run worker:dev`. В Docker Compose app ждёт БД и применяет миграции, worker ждёт readiness app.

Production: HTTPS reverse proxy, приватная PostgreSQL, закрытая Google-таблица, разрешённые менеджеры, секреты через окружение. `NODE_ENV=production`, `INTEGRATION_MODE=live`, `PAYMENT_PROVIDER=freedompay`, `FREEDOMPAY_TEST_MODE=false`. `/dev/*` отсутствуют. `check:production` и ручная проверка аккаунтов обязательны до приёма клиентов. Неполные бизнес-данные блокируют checkout, но не приём callback по уже существующей оплате.

Время хранится/сравнивается в UTC; соединения PostgreSQL явно задают `timezone=UTC`. Интерфейс показывает время для Asia/Almaty. Не меняйте часовую зону сессии worker: raw SQL очереди использует `now()`.

## Очереди и диагностика

`GET /health` проверяет HTTP-процесс, `GET /ready` — доступ к БД. `GET /admin/status` с `Authorization: Bearer <ADMIN_TOKEN>` показывает состояния inbox/outbox, платежи, инциденты, задержку Sheets и heartbeat. Worker публикует heartbeat на каждом проходе; старше120 сек считается отсутствующим. Мониторинг должен читать этот endpoint независимо от Telegram.

Inbox: RECEIVED → PROCESSING → PROCESSED; ошибки → RETRY, затем DEAD. Outbox: PENDING → PROCESSING → DONE; временная известная ошибка → RETRY; запрет/некорректная конфигурация → BLOCKED; неоднозначная отправка → UNKNOWN; исчерпанные попытки → DEAD. Lease60 сек, обновление проверяет токен владельца. Истёкший lease после начала WhatsApp/Telegram/create-payment не доказывает отсутствие внешнего эффекта и переводится в UNKNOWN.

Повторы:60/300/900/3600 сек с небольшим jitter, учитывается больший Retry-After; до8 выполнений. Закрытое окно и запрет согласия не обходятся повтором. Ошибка Sheets не откатывает оплату и не задерживает платёжную сверку. Внешняя система может завершить старый запрос после lease: fencing защищает локальное состояние; периодическая сверка восстанавливает актуальную строку Sheets.

`POST /admin/jobs/:id/retry` — ручной повтор с audit. Для UNKNOWN сообщения требуется JSON `{ "acknowledgeDuplicateRisk": true, "actor": "operator-id", "comment": "Результат сверки" }`: повтор может отправить дубль. Неизвестное создание платежа этим endpoint повторить нельзя; используйте сверку. Не отправляйте UNKNOWN повторно только потому, что сообщение отсутствует в интерфейсе.

`POST /admin/inbox/:id/retry`, `/admin/orders/:id/check-payment`, `/admin/orders/:id/resync-sheet`, `/admin/customers/:id/release-handoff` требуют тот же bearer. Для устранения инцидента: `POST /admin/incidents/:id/resolve` с `{ "actor": "operator-id", "comment": "Проверено ...", "releaseHold": true }`. Hold снимается только при отсутствии остальных открытых инцидентов. Закрытие обращения и возврат к боту финансовый hold не снимают.

## Платежи

Подтверждение создаёт одну сохранённую попытку и одно задание. Snapshot попытки (сумма, валюта, заказ, версия, merchant reference) неизменяем и защищён триггером БД. Провайдерский API-успех, сообщение клиента и браузерный redirect сами по себе не делают заказ оплаченным.

CREATION_UNKNOWN сверяется по сохранённой ссылке/идентификатору. Новая попытка допустима после подтверждённого терминального результата. REVIEW_REQUIRED требует расследования; одного закрытия уведомления недостаточно для признания предыдущей попытки неоплаченной. Полученная старая ссылка учитывается по своей попытке. Вторая реальная оплата сохраняется отдельным поступлением с инцидентом и hold. Оплата отменённого заказа сохраняет CANCELLED. Возвраты не отправляются автоматически.

`PAYMENT_RECONCILE_INTERVAL_MS=300000`, `PAYMENT_RECONCILE_BATCH_SIZE=100`, `PAYMENT_PROVIDER_MIN_INTERVAL_MS=2000` задают период/пакет/частоту запросов статуса. Сохранённые незавершённые callbacks тоже восстанавливаются worker после сбоя. Не подтверждайте инцидент по неподписанным данным или скриншоту.

## Миграция прежней установки

1. Остановить app/worker и приостановить входящий трафик на короткое окно обслуживания. Сохранить БД, конфигурацию и текущий release; проверить возможность восстановления.
2. Применить `npm run db:migrate`. Миграции сохраняют существующие оплаты, помечают legacy-строки Sheets для сверки, не создают реальные платежи и не рассылают прежние подтверждения. Если ограничения выявили конфликт активных попыток — расследовать записи, не удалять их для обхода ограничения.
3. Для прежних Freedom Pay records выполнить `npx tsx scripts/migrate-payments.ts` и проверить отчёт. Затем `npx tsx scripts/migrate-payments.ts --apply` переносит настроенный merchant ID только в помеченные legacy-записи. Старый reference принимается только с совпадающим известным externalPaymentId.
4. Для Google Sheets выполнить `npm run sheets:migrate`. Отчёт `.local/sheet-migration-report.json` содержит совпадения/дубли/несоответствия. При конфликте автоматическое применение прекращается. После проверки — `npm run sheets:migrate -- --apply`. Импорт создаёт постоянные bindings и обновление отчёта без повторных платёжных уведомлений. Курсор никогда не перематывается назад.
5. Проверить25 заголовков A:Y и защиту Orders, затем production readiness. Запустить app и worker; проверить diagnostics и исторические оплаты.

Для технического листа запрещены физическая сортировка, вставка/удаление/перестановка строк. Сделайте отдельный Orders_View для фильтров/сортировки. Не снимайте защиту технического листа ради успешного задания: сначала восстановите его структуру и идентификаторы.

## Резервное копирование и восстановление

Для серверной PostgreSQL используйте штатные `pg_dump`/`pg_restore` той же или совместимой версии клиента. Секреты передавайте через закрытый `.pgpass`/секрет окружения, а не в историю команд.

```sh
pg_dump --format=custom --file=musicbox.backup "$DATABASE_URL"
# Только заранее созданная отдельная пустая база для проверки восстановления:
pg_restore --exit-on-error --no-owner --dbname="$RESTORE_DATABASE_URL" musicbox.backup
```

Восстановление выполняют в отдельную БД; проверяют количество заказов/попыток, appliedPaymentAttemptId, инциденты, inbox/outbox, SheetBinding и версии, затем запускают тестовый сервис с закрытым внешним egress и выключенными реальными отправками. Сохраняйте задания DONE и ключи дедупликации: их удаление может вызвать повторные действия. Для переключения production повторно остановите старые процессы, проверьте целевые секреты и восстановленную очередь; не держите две копии одной восстановленной базы с активными внешними отправками.

Локальная встроенная PostgreSQL не включает pg_dump. Для неё допустима физическая копия **после полной остановки** `npm run demo`; копировать `.local/postgres` в отдельный каталог, использовать ту же версию PostgreSQL 18 и другой порт. Живую директорию файлов базы простым `cp`/`tar` не копируют. Автотест T30 останавливает тестовую PostgreSQL, копирует каталог, запускает копию на другом порту и проверяет сохранённую запись и миграции.

Перед v1.1 в этой рабочей папке сохранены `.local/backups/pre-v1.1-postgres.tar.gz` и `implementation-start-source.tar.gz` — промежуточный архив исходников начала работы, не готовый release для отката. Эти локальные архивы содержат персональные данные демонстрации; не публикуйте их вместе с репозиторием. В production задайте расписание, шифрование, отдельное хранилище и регулярную проверку восстановления по политике владельца.

## Данные и доступ

До имени/адреса бот показывает локализованное уведомление с версией. Согласие на инициативные WhatsApp-уведомления хранится отдельно; STOP его отзывает без отмены заказа. Настройте опубликованную privacy policy и контакт бизнеса. Содержимое FAQ не получает адрес/телефон заказа, secrets и платёжные payload.

`RETENTION_APPROVED=false` по умолчанию. После утверждения владельцем сроков/размещения/доступа и порядка удаления установить true и согласованные `MESSAGE_RETENTION_DAYS`, `WEBHOOK_RETENTION_DAYS`. Worker очищает содержимое старых сообщений и завершённых нефинансовых webhook, сохраняя ключи дедупликации. Финансовые события, суммы, попытки, инциденты и история принятия решений автоматически этой очисткой не удаляются. Сроки по умолчанию — настройки демонстрации, а не юридическое заключение.
