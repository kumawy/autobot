# Проверка staging через официальный WhatsApp Cloud API

Staging использует настоящий Meta Cloud API и OpenAI, демонстрационный каталог и только mock-платежи. Сообщения действительно уходят в WhatsApp; OpenAI получает текст консультации. Google Sheets и Telegram можно оставить отключёнными. Это не локальный симулятор и не разрешение принимать реальные платежи.

Статус на 1 октября 2026 года: код проверяется автоматическими тестами с подменённым HTTP. Реальный обмен с Meta ещё не проверен: нужны параметры приложения, разрешённый тестовый получатель и публичный HTTPS-адрес. Эта инструкция описывает тестовый номер Meta; она не требует завершить business verification перед таким тестом и не заявляет, что проверка бизнеса уже пройдена. Конкретные ограничения аккаунта смотрите в панели Meta.

## 1. Подготовить тестовые ресурсы Meta

В Meta for Developers откройте своё приложение с WhatsApp и раздел **WhatsApp → API Setup / Getting Started**. Используйте предоставленный тестовый номер. Добавьте свой тестовый номер получателя в доступный в панели список и выполните предлагаемый способ подтверждения. Сохраните **Phone number ID** и **WhatsApp Business Account ID (WABA ID)**: это разные идентификаторы, не отображаемый телефон. Токен из Getting Started подходит для первоначального теста; пользовательский временный токен ограничен по сроку, поэтому перед проверкой убедитесь, что он действителен. [Официальная коллекция Meta: ресурсы, токены и разрешения](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api?entity=request-13382743-071cfa60-0704-41d2-bca2-36ba6bd33dfe).

Заполните локальный `.env.staging.local`, который исключён из Git. Не вставляйте ключи в чат, URL, скриншоты или README.

| Переменная проекта                   | Что указать                                                                                |
| ------------------------------------ | ------------------------------------------------------------------------------------------ |
| `WHATSAPP_ACCESS_TOKEN`              | Действующий токен приложения для тестового номера                                          |
| `WHATSAPP_PHONE_NUMBER_ID`           | Phone number ID выбранного отправителя                                                     |
| `WHATSAPP_WABA_ID`                   | WABA ID, которому принадлежит номер                                                        |
| `WHATSAPP_GRAPH_API_VERSION`         | Поддерживаемая версия Graph API из примера в вашей панели, в формате `vNN.N`               |
| `WHATSAPP_APP_SECRET`                | App Secret этого же приложения; используется проверкой подписи POST                        |
| `WHATSAPP_VERIFY_TOKEN`              | Собственная случайная строка для проверки callback; такая же строка вводится в панели Meta |
| `OPENAI_API_KEY`, `OPENAI_MODEL`     | Ваш проектный ключ и доступная модель                                                      |
| `DATABASE_URL`                       | База staging, отдельная от будущей production-базы                                         |
| `APP_BASE_URL`                       | Публичный HTTPS origin staging без пути webhook                                            |
| `ADMIN_TOKEN`, `MOCK_PAYMENT_SECRET` | Независимые случайные локальные секреты, не токены Meta                                    |

Номер и временный токен находятся в Getting Started. Ответ получателя на тестовое сообщение открывает окно общения для обычных ответов; вне окна используются разрешённые шаблоны. Старый SDK устанавливать не нужно: проект вызывает Cloud API своим HTTP-клиентом. [Официальный Quickstart Meta, архивный SDK](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/).

## 2. Запустить staging

Используйте Node.js **24.21.0**. В локальном конфиге:

```dotenv
NODE_ENV=development
INTEGRATION_MODE=staging
PAYMENT_PROVIDER=mock
DEV_ROUTES_ENABLED=false
GOOGLE_SHEETS_ENABLED=false
TELEGRAM_ENABLED=false
MANAGER_HANDOFF_ENABLED=false
```

После заполнения остальных обязательных значений:

```sh
DOTENV_CONFIG_PATH=.env.staging.local npm run db:generate
DOTENV_CONFIG_PATH=.env.staging.local npm run db:migrate
DOTENV_CONFIG_PATH=.env.staging.local npm run dev
```

Во втором терминале с тем же конфигом запустите worker:

```sh
DOTENV_CONFIG_PATH=.env.staging.local npm run worker:dev
```

HTTP-процесс сохраняет входящие события и подтверждает приём. Worker обрабатывает их и отправляет ответы; без него бот не ответит.

`npm run demo` запускает локальные заглушки и для проверки Meta не подходит. При отключённой передаче менеджеру бот сообщает об этом на RU/KK, сохраняет текущий шаг заказа и не создаёт обращение с обещанием человеческого ответа.

Проверьте локальный `/health`, затем настройте свой HTTPS reverse proxy или туннель до приложения. Публичные `/dev/*` и симулятор в staging отсутствуют; `DEV_ROUTES_ENABLED=true` разрешён только в режиме demo. Endpoint администратора защищён `ADMIN_TOKEN`; не передавайте этот токен Meta. Требование публичного HTTPS endpoint приведено в [официальной документации Meta о приёме сообщений](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/receivingMessages/).

## 3. Настроить callback

В настройке Webhooks приложения укажите:

- Callback URL: `https://ВАШ-STAGING-ДОМЕН/webhooks/whatsapp`.
- Verify token: значение `WHATSAPP_VERIFY_TOKEN`.
- Объект WhatsApp Business Account, поле **messages** — входящие сообщения и события их статуса.

Сохранение callback вызывает GET challenge. Проект сверяет verify token и возвращает `hub.challenge`. Последующие POST проверяются по `X-Hub-Signature-256` и App Secret на исходных байтах тела: proxy не должен изменять JSON перед приложением. Verify token не заменяет App Secret. [Официальное описание проверки GET и POST Meta](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/webhooks/start/).

Проверьте также подписку приложения на нужный WABA: она отличается от проверки URL. Официальная коллекция содержит `GET /{WABA-ID}/phone_numbers` и `POST /{WABA-ID}/subscribed_apps`; используйте их при диагностике с токеном своего приложения. [Официальные запросы Meta](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api?entity=request-13382743-29aebcc2-6601-4b2a-ad35-afca7745b2a1).

## 4. Провести реальный тест владельцем

1. В панели Meta отправьте тестовое сообщение на свой разрешённый номер и ответьте на него из WhatsApp. Убедитесь, что ответ пришёл на callback, а не только сработала кнопка проверки URL. [Официальный Send Test Message](https://www.postman.com/meta/whatsapp-business-platform/request/9php9mt/send-test-message).
2. Напишите «Сколько стоит?». Выберите RU: ожидаются меню и ответ на сохранённый первый вопрос. Повторите отдельный диалог с KK.
3. Задайте вопрос по каталогу. Неизвестные условия должны остаться неизвестными; просьба вызвать менеджера возвращает сообщение о недоступной функции, после которого можно продолжать заказ.
4. Начните заказ. Проверьте уведомление о данных и отдельное согласие. Вводите вымышленные имя и адрес. Телефон WhatsApp для самого теста должен быть вашим разрешённым номером.
5. Пройдите имя → телефон → город → адрес → список мелодий → «Готово» → количество. Проверьте состав, стоимость товаров, отдельную доставку и общую сумму. Попробуйте «Назад», смену языка и отмену с подтверждением.
6. Подтвердите тестовый заказ. Бот пришлёт подписанную ссылку `/mock-payment/{attemptId}` с ограниченным сроком действия. Это отдельная staging-страница, а не `/dev/*`; без правильной подписи и срока она возвращает 403. Никаких реквизитов карты или настоящей оплаты: кнопки «Успешная оплата» / «Отказ» создают тестовое событие. Сначала напишите «я оплатил» и убедитесь, что статус не стал PAID. Затем выберите тестовый успех на странице и дождитесь подтверждения в WhatsApp. Деньги не списываются; ссылку не публикуйте, она разрешает изменение конкретного тестового платежа.
7. Сопоставьте исходящий `wamid` и callback статуса. `ACCEPTED` означает принятие API; `DELIVERED`/`READ` появляются только при соответствующем событии Meta. Повтор одного входящего `wamid` не создаёт ещё один заказ или ответ.
8. Напишите «стоп». Уведомления отключаются; заказ сохраняется, ответы на новые сообщения продолжаются.

Запишите дату, выбранный язык, ID заказа, ожидаемый и фактический результат. Ключи, тексты реальных клиентов и полные webhook-тела в отчёт не копируйте. До фактического выполнения этих шагов результат остаётся **«реальный Meta smoke-test не выполнен»**.

## Диагностика

| Признак                                 | Что проверить                                                                         |
| --------------------------------------- | ------------------------------------------------------------------------------------- |
| GET callback не подтверждается          | HTTPS, точный путь, verify token, доступность приложения                              |
| POST получает 401                       | App Secret того же приложения, исходные байты JSON, подпись; не отключать проверку    |
| Meta сообщает ошибку токена             | Срок и разрешения токена, соответствие приложению и номеру                            |
| Тестовая кнопка работает, сообщений нет | Подписки `messages` и WABA, разрешённый получатель, правильный Phone number ID        |
| API принял запрос, сообщения ещё нет    | Callback статуса и код ошибки доставки; принятие API не равно доставке                |
| Задание UNKNOWN                         | Исход запроса неоднозначен после таймаута/5xx; не повторять отправку вслепую          |
| Нет записи в Sheets или Telegram        | Для этого staging-профиля интеграции намеренно выключены; заказ хранится в PostgreSQL |

Проверка источников: актуальная официальная коллекция Meta в Postman доступна. Основные страницы `developers.facebook.com` при подготовке вернули HTTP 429; архивные страницы Meta SDK использованы только для описания callback и тестового диалога, не для версий Node.js, SDK или Graph API.
